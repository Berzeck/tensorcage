# TensorCage 2.0.2

## Summary

TensorCage 2.0.2 completes the migration to the unified Bittensor 11
runtime and replaces preload-based WebSocket interception with native
asynchronous SOCKS transport.

The release preserves the existing fail-closed containment model:

- direct user egress remains blocked;
- Bittensor traffic traverses the local Dante SOCKS service;
- DNS remains restricted through managed Unbound policy;
- PyPI access opens only during explicit, hash-locked update operations;
- managed configuration integrity is verified after deployment.

## Runtime versions validated

The production validation on `bcs-001` used:

- TensorCage 2.0.2;
- Bittensor 11.0.1;
- bittensor-core 0.1.1;
- Python 3.13;
- websockets 16.1.1;
- python-socks 2.8.2.

The complete approved Bittensor environment contained 34 locked wheel
distributions.

## Stability improvements

Two production-discovered issues were corrected before this release was
finalized:

- EXIT-trap cleanup state is preserved after shell function scope
  unwinds;
- temporary PyPI destinations are resolved through the managed Unbound
  resolver instead of ambient NSS or resolver state.

Both corrections were discovered and validated during real deployment
and failure-path testing rather than through syntax checks alone.

## Native asynchronous SOCKS transport

Bittensor 11 uses an asynchronous WebSocket implementation that was not
reliably compatible with Dante's `socksify` preload interception.

TensorCage 2.0.2 changes the `btc` wrapper to use the proxy support
provided by `websockets` and `python-socks`:

~~text
btc
  -> Bittensor 11
  -> websockets native proxy support
  -> python-socks
  -> Dante at 127.0.0.1:1080
  -> approved Bittensor destination
~~

The wrapper configures:

~~text
wss_proxy=socks5h://127.0.0.1:1080
ws_proxy=socks5h://127.0.0.1:1080
no_proxy=127.0.0.1,localhost,::1
~~

`socksify` remains available for controlled synchronous diagnostics and
the secured wheel-download workflow, but it is no longer used for
Bittensor's asynchronous WebSocket connection.

## Secured Bittensor update workflow

The release updates the Bittensor installation workflow to require a
complete hash-locked wheel set.

The workflow:

1. validates the supplied lock file and its separately supplied SHA-256;
2. temporarily opens only the required PyPI DNS and Dante destinations;
3. downloads only binary wheels with mandatory hashes;
4. verifies exact wheel membership and every wheel SHA-256;
5. installs only from the verified local wheel directory with no index;
6. verifies the installed Bittensor and native SOCKS versions;
7. rejects the superseded `bittensor-cli` and `bittensor-wallet`
   packages;
8. re-closes PyPI access;
9. refreshes and validates managed configuration integrity.

The temporary PyPI allowlist exists only for the verified download
transaction. Cleanup restores the default closed policy on both success
and failure paths.

The locked workflow substantially reduces exposure to:

- dependency confusion;
- unexpected dependency upgrades;
- artifact substitution after approval;
- missing, extra, or partially downloaded wheel sets;
- accidental source-distribution installation.

The deployment used a fully hash-locked wheel manifest generated by
TensorCage's secured lock workflow.

The exact lock artifact is deployment-local, intentionally excluded from
the Git repository, and may differ between approved Bittensor releases
without requiring changes to this document.

## Managed Unbound destination resolution

Temporary PyPI destination addresses are now resolved explicitly through
the managed Unbound service at `127.0.0.1`.

The resolver:

- waits for Unbound readiness after policy changes;
- retries within a bounded interval;
- requires every configured PyPI hostname to resolve;
- accepts only IPv4 address results;
- refuses to open the update window if any required hostname cannot be
  resolved.

This avoids depending on ambient NSS or resolver configuration and keeps
the update transition fail-closed.

## Lock-create cleanup reliability

The `lock-create` EXIT trap now retains its cleanup state after the
calling function unwinds.

The correction ensures that failure paths can still:

- determine whether the temporary PyPI policy may be open;
- restore the closed policy;
- remove the temporary download directory;
- remove the temporary lock file;
- avoid undefined-variable failures under strict shell settings.

Both expected failure and successful secured-host paths were validated.

## Doctor improvements

TensorCage Doctor now additionally validates:

- that the `btc` wrapper uses native asynchronous SOCKS transport;
- that the `python-socks` backend is installed;
- that a Bittensor WebSocket handshake succeeds through Dante.

## Compatibility and operational notes

Bittensor 11 changes several CLI command names and options. Existing
Bittensor 9-era aliases and transaction commands may require migration.

Read-only chain, wallet, and subnet operations were validated.
Operational commands should continue to be reviewed against future
Bittensor releases because upstream CLI syntax and transaction interfaces
may evolve independently of TensorCage.

## Known limitations and future work

This release does not prove that every approved third-party wheel is free
from vulnerabilities or malicious upstream behavior.

Hash locking guarantees reproducibility and artifact integrity after lock
generation, but it cannot prove that an upstream release was benign when
the lock was created.

Trust in upstream publishers therefore still exists during lock
generation. Future TensorCage milestones aim to reduce that trust through
advisory review, offline release signing, software bills of materials
(SBOMs), provenance recording, and signed approval reports.

Planned supply-chain improvements include:

- advisory scanning of every locked distribution;
- offline cryptographic signing of TensorCage releases and lock files;
- signed approval reports;
- software bill of materials and provenance records.

Those improvements are separate milestones and are not required for the
validated TensorCage 2.0.2 deployment.
