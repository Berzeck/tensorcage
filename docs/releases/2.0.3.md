# TensorCage 2.0.3

## Summary

TensorCage 2.0.3 corrects a system-dependency defect in the firewall
containment installation and lifecycle validation.

TensorCage 2.0.2 configured firewalld direct rules but did not explicitly
install the openSUSE compatibility packages required to instantiate those
rules. On a minimal openSUSE Leap 16 installation, this could leave the
permanent rule configuration present while the corresponding runtime rules
were unavailable.

The corrected release fails closed unless the required firewall
compatibility environment is installed and operational.

## Corrected system dependencies

The baseline installer now explicitly installs:

- `iptables`;
- `xtables-plugins`.

The release validates the presence of:

- `firewalld`;
- `iptables`;
- `nftables`;
- `xtables-plugins`.

It also validates the canonical IPv4 and IPv6 command paths:

- `/usr/sbin/iptables`;
- `/usr/sbin/ip6tables`;
- `/usr/sbin/iptables-restore`;
- `/usr/sbin/ip6tables-restore`.

Each path must be executable, root-owned, RPM-owned, and operational with
the `nf_tables` backend.

## Required xtables functionality

TensorCage verifies the root-owned, RPM-managed xtables modules used by its
firewall policy:

- `libxt_LOG.so`;
- `libxt_conntrack.so`;
- `libxt_owner.so`.

This covers logging, established-connection handling, and process-owner
egress restrictions.

## Fail-closed firewall validation

The firewall lifecycle now verifies:

- availability of the firewalld IPv4 direct backend;
- availability of the firewalld IPv6 direct backend;
- the permanent IPv4 terminal OUTPUT drop;
- the permanent IPv6 terminal OUTPUT drop;
- the runtime IPv4 terminal OUTPUT drop;
- the runtime IPv6 terminal OUTPUT drop.

Validation occurs before firewall policy configuration and again after the
firewalld reload that materializes the runtime rules.

A successful install or enable operation therefore cannot report success
when the permanent configuration exists but the live direct-rule backend
is unavailable.

## Lifecycle and diagnostic integration

The compatibility checks are integrated into:

- installation;
- enable and firewall reconciliation;
- lifecycle status classification;
- TensorCage Doctor;
- the focused firewall self-test.

TensorCage Doctor now includes two additional firewall dependency checks.
The validated result is:

~~~text
PASS=44
WARN=0
FAIL=0
Overall: PASS
~~~

## Persistent-state hardening

The TensorCage state directory and rollback root are explicitly enforced as
regular directories owned by `root:root` with mode `0700`.

Rollback snapshot creation now:

- rejects symbolic links and non-directory state paths;
- corrects the rollback-root owner and mode before use;
- verifies exact `root:root 0700` metadata;
- rejects a timestamped destination that already exists;
- creates each snapshot tree as root-private state.

The parent state directory already prevented unprivileged traversal. This
change makes the rollback-root metadata independently consistent with the
same defense-in-depth policy.

## Version compatibility

This release changes only the TensorCage application version:

~~~text
Application:   2.0.3
Policy:        6
Configuration: 7
Manifest:      2
~~~

The policy, generated configuration format, and integrity-manifest format
remain unchanged.

## Validation performed

The dependency helpers were first validated read-only on the unrestricted
development workstation.

The exact candidate was then transferred by SHA-256 to a private staging
directory on the protected reference host and validated against the live
deployment.

The protected-host validation confirmed:

- exact candidate SHA-256 identity;
- 30 runtime firewalld direct rules;
- 30 permanent firewalld direct rules;
- successful IPv4 and IPv6 direct-backend checks;
- successful focused firewall dependency test;
- TensorCage Doctor with 44 passes and no warnings or failures;
- no managed-file content or metadata drift;
- byte-identical runtime firewalld state before and after testing;
- byte-identical permanent firewalld state before and after testing;
- byte-identical TensorCage nftables state before and after testing;
- all required services remained enabled and active.

The installed TensorCage 2.0.2 executable remained unchanged throughout
staged validation.

This release adds a concise installed-filesystem summary to `README.md`
and a complete operational inventory in
`docs/installation-layout.md`.

The detailed reference documents:

- all nine integrity-managed files;
- executable and Python-runtime locations;
- persistent lifecycle, integrity, and rollback state;
- expected ownership and modes;
- generated systemd integration;
- transient `/run` material;
- externally modified DNS, proxy, firewalld, and nftables state;
- required operating-system packages;
- preserved wallet boundaries;

- install, enable, disable, and uninstall behavior.

A dependency-free repository regression test at

- exact agreement between `managed_integrity_paths()` and the detailed
  integrity-managed table;
- complete managed-path coverage in the README summary;
- required persistent, runtime, systemd, external-configuration, package,
  and wallet-boundary documentation;
- the distinction between baseline installation and the separately locked
  Bittensor runtime workflow.

The documentation distinguishes source-defined guarantees from metadata
observed on the validated openSUSE Leap 16 reference host.

## Deployment and rollback requirements

The production deployment procedure must:

- preserve the previously installed executable;
- preserve the existing managed-integrity manifest;
- stage the replacement inside `/usr/local/bin`;
- perform the final rename within `/usr/local/bin`;
- reconcile TensorCage through the normal enable lifecycle;
- refresh and verify the managed-integrity manifest;
- restore the previous executable and integrity manifest if any validation
  step fails.

## Scope

This release does not change the installed Bittensor environment, wallet
data, DNS policy, approved network destinations, or cryptographic lock
manifest.

Advisory scanning, offline release signing, SBOM generation, provenance
recording, and signed approval reports remain separate future milestones.
